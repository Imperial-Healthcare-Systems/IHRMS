# IHRMS-2 — Full Project Review

**Date:** 2026-09-06
**Scope:** whole repo — 116 API routes, 33 pages, 22 lib modules, middleware, config, build health
**Method:** manual read of auth/session plumbing, every route's authorization posture, cross-route consistency checks, `tsc --noEmit`, `next build`

---

## Verdict

**Not production-deployable as-is.** Three classes of problem:

1. **The production build fails.** (blocker)
2. **Two functional systems are silently dead** — in-app notifications, and any account that has ever been impersonated.
3. **A cluster of authorization gaps** where the middleware gates the *page* but the *API route* behind it is open to any authenticated employee.

The multi-tenant foundation itself is solid: 115 of 116 routes filter by `ctx.orgId`, `getActiveEmployee()` correctly resolves `identities.id → employees.id` in 24 routes, the service-role client is `server-only`-guarded, and `tsc --noEmit` is clean.

## Blocker

### B1. `next build` fails — cannot deploy

`components/team-attendance/DevTenantSwitcher.tsx:26-34` calls seven `useState`s and a `useEffect` *after* an early `if (!IS_DEV) return null` (line 24). That is `react-hooks/rules-of-hooks`, which `next lint` treats as an **error**, so `next build` exits non-zero.

```
./components/team-attendance/DevTenantSwitcher.tsx
26:27  Error: React Hook "useState" is called conditionally.  (x7)
34:3   Error: React Hook "useEffect" is called conditionally.
176:163 Error: ' can be escaped with &apos;
```

Plus one warning in `app/(modules)/recruitment/page.tsx:300` (`useMemo` missing dep `funnelStages`).

**Fix:** move the hooks above the guard and gate the *render*, not the hook calls:

```tsx
export default function DevTenantSwitcher() {
  const [open, setOpen] = useState(false)
  // ...remaining hooks
  useEffect(() => {
    if (!IS_DEV || !open || tenants !== null) return
    // ...
  }, [open, tenants])

  if (!IS_DEV) return null
  // ...render
}
```

Tree-shaking still works: the render body is still dead code behind the constant, and `/api/dev/tenants` keeps its runtime 404 gate. Escape the apostrophe at line 176.

This has been broken since at least 2026-05-30 (noted in the auth-migration handover) and is still broken 3 months later.

## Critical

### C1. Impersonation permanently bricks the target account

`app/api/auth/impersonation-login/route.ts:191-193` writes `is_impersonating: true`, `impersonator_admin_id`, `impersonation_log_id` into the **target user's** `auth.users.app_metadata`.

`app/api/auth/impersonation-end/route.ts` closes the log row and calls `signOut()` (line 59) — but **never clears those three keys**. Grepping the whole repo, `is_impersonating` is written in exactly one place and cleared in none.

Supabase's `admin.updateUserById({ app_metadata })` **merges** keys, it does not replace them. So the stale flags survive every subsequent login — including `verify-otp`'s metadata write (line 156), which never mentions `is_impersonating`.

The failure chain:

1. Imperial admin impersonates employee X, then ends the session. `platform_impersonation_log.ended_at` is now set.
2. X's `app_metadata` still says `is_impersonating: true`, `impersonation_log_id: <that closed row>`.
3. X logs in normally. `verify-otp` succeeds, cookies are set, `/dashboard` renders.
4. Every API call runs `requireAuth()` → `getSession()` → `lib/session.ts:76-88` sees `is_impersonating` plus a log row with non-null `ended_at` → **`signOut()` and return null** → 401.

X can log in but nothing works, forever, with no error message that explains why. The only recovery is a manual `app_metadata` edit in Supabase.

The code comment at `impersonation-login/route.ts:186` ("replaces previous metadata so a half-finished impersonation can't leak claims forward") is incorrect for the same merge-vs-replace reason.

**Fix:** in `impersonation-end`, before `signOut()`, null out the keys:

```ts
await supabaseAdmin.auth.admin.updateUserById(user.id, {
  app_metadata: {
    is_impersonating: null,
    impersonator_admin_id: null,
    impersonation_log_id: null,
  },
})
```

(Supabase deletes keys whose value is `null`.) Belt-and-braces: also set them to `null` in the `verify-otp` metadata write so a normal login self-heals a stuck account.

### C2. In-app notifications are written with the wrong key — 4 of 5 producers are dead

The reader, `app/api/notifications/route.ts:26`, filters `.eq('recipient_id', ctx.identityId)` — **identities.id**.

The writers:

| Producer | File:line | Writes |
|---|---|---|
| Announcement fan-out | `announcements/route.ts:45` | `emp.id` — employees.id ✗ |
| Regularization decision | `attendance/regularization/route.ts:215` | `reg.employee_id` ✗ |
| Exit process update | `exit/route.ts:231` | `exitRow.employee_id` ✗ |
| Leave approve/reject | `leaves/[id]/route.ts:27` | `employeeId` (= `row.employee_id`) ✗ |
| CRM deal closed | `ecosystem/consume/route.ts:43` | `emp.identity_id` ✓ |

`notifications POST` (`notifications/route.ts:92-95`) even *validates* `recipient_id` against `employees.id` — so the manual-notification path is wrong too, and cements the inconsistency.

Net effect: every announcement, leave decision, regularization decision and exit update writes a notification row **no one can ever see**. The bell icon shows 0. Nothing errors; the rows accumulate silently. Only the ICRM deal-closed path works, and only because `ecosystem/consume` was individually fixed — its comment at lines 35-37 documents this exact mismatch, but the fix was applied there and nowhere else.

**Fix:** pick one convention. Cheapest is to resolve `employee_id → identity_id` in the four producers (mirror `ecosystem/consume`). Cleaner is to store both `recipient_identity_id` and `recipient_employee_id` and read on the former. Either way, backfill or discard the orphaned rows.

## High

### H1. Any employee can read any colleague's attendance — including GPS coordinates

`app/api/attendance/route.ts:83`:

```ts
if (employee_id) {
  query = query.eq('employee_id', employee_id)          // <- no role check
} else if (!FULL_ACCESS_ROLES.includes(ctx.role)) {
  const me = await getActiveEmployee(...)
  query = query.eq('employee_id', me.id)
}
```

Self-scoping applies only when `employee_id` is **absent**. `GET /api/attendance?employee_id=<colleague-uuid>` returns their full history, and the select at line 74 includes `geo_lat, geo_lng, geo_location` — an employee can pull a coworker's daily location trail.

This is an outlier, not a design decision: `leaves/route.ts:47-61`, `reimbursements/route.ts:71`, `documents/route.ts:48-49` and `attendance/summary/route.ts:56-58` all gate the same parameter by role correctly.

**Fix:** apply the sibling pattern — only honour `employee_id` when `FULL_ACCESS_ROLES.includes(ctx.role)`, or when the target is in the caller's reporting line.

### H2. Any employee can punch in/out as any colleague

`app/api/attendance/route.ts:120-131` — POST accepts `employee_id` from the body, and the only check is that the target is in the same org. No role gate. An employee can mark a colleague present or absent, on any device, at any time. Direct attendance/payroll fraud vector.

Same shape in `app/api/leaves/route.ts:111-124` — an employee can file a leave request in a colleague's name.

**Fix:** in both routes, reject a body `employee_id` that differs from `me.id` unless the caller is HR/admin or the target's reporting manager.

### H3. Leave cancellation has no authorization check at all

`app/api/leaves/[id]/route.ts:134`. The `approve`/`reject` branch (lines 116-132) correctly requires HR or the reporting manager. The `cancel` branch has none — it only requires that the row exists in the caller's org. Any authenticated employee can cancel anyone's approved leave.

Worse in combination: the approved leave's balance was already decremented, and cancelling does **not** credit it back — so the victim loses the leave days *and* the time off.

### H4. Approving a leave twice double-decrements the balance

`app/api/leaves/[id]/route.ts:150-158` updates `status: 'approved'` unconditionally — no check of the current status. Two PATCHes with `action: 'approve'` (double-click, retry, two managers) run the balance decrement twice. Same for approving a request that was already `cancelled` or `rejected`.

**Fix:** add `.eq('status', 'pending')` to the update and 409 when zero rows come back. That makes the transition atomic and idempotent without needing a transaction.

### H5. Middleware gates pages; the APIs behind them are open to every employee

The `middleware.ts` matcher (lines 92-110) covers only page paths — `/payroll/:path*`, `/recruitment/:path*` and so on. It **never matches `/api/*`**. So the role map is advisory: the data is one `fetch` away for any logged-in employee.

Confirmed unprotected (`requireAuth()` only, no internal role check):

| Route | Exposes |
|---|---|
| `recruitment/candidates/route.ts:17` | candidate PII, `current_ctc`, `expected_ctc`, resumes |
| `recruitment/interviews/route.ts:16,63,128` | interview schedules and panel |
| `recruitment/feedback/route.ts:7,55` | interviewer scorecards |
| `payroll/route.ts:23` | every payroll run for the org |
| `billing/subscription`, `billing/invoices`, `billing/credits` | org billing state, invoice history |
| `exit/route.ts` | exit/resignation processes |
| `assets/route.ts` | asset register |

`payroll/salary-structures` and `payroll/[id]` are correctly on `requireRole` — so the pattern is understood, just applied inconsistently.

**Fix:** put `requireRole(...)` on each of these to mirror its middleware entry. Do not rely on the middleware for API authorization.

### H6. Any employee can read any colleague's HR documents

`app/api/employees/[id]/documents/route.ts:15-33` — GET checks only that the target employee is in the caller's org, then returns every `employee_documents` row: Aadhaar, PAN, bank proofs, education certificates. No self-or-HR check. POST (line 49) is the same, so an employee can also *upload* documents into a colleague's file.

Contrast `documents/download/route.ts:26-32`, which does this correctly (`HR_ROLES` or owner-only), and `training/[id]/stream/[contentId]/route.ts:33-47`, also correct.

**Fix:** copy the `documents/download` gate — `HR_ROLES.includes(ctx.role) || id === me.id`.

## Medium

### M1. Unauthenticated attacker can log any user out of every device, repeatedly

`app/api/auth/verify-otp/route.ts:156` calls `admin.updateUserById()` **before** OTP verification (line 187). The header comment acknowledges the tradeoff, but understates it: `updateUserById` **invalidates all existing refresh tokens** for that user.

So `POST /api/auth/verify-otp {email: victim@co, otp: "000000"}` — no session, no valid OTP needed — terminates every one of the victim's live sessions. Loop it and the victim can never stay logged in. It also resets their active org to `last_active_org_id`, undoing an org switch.

The rate limit that "caps blast radius" lives in `/api/auth/otp` (line 30), a *different route*. `verify-otp` has none.

**Fix:** the ordering constraint is real (documented in both the ICRM and IHRMS handovers), so keep it — but add a per-email rate limit on `verify-otp` itself, and better, only write metadata when the incoming OTP is well-formed *and* a pending challenge exists for that email.

Related: the `/api/auth/otp` cooldown (lines 33-36) is an in-memory `Map` on `globalThis`. On Vercel that is per-lambda-instance — under any concurrency it barely rate-limits at all. Move it to Postgres or Upstash.

### M2. Cron endpoints are open if `CRON_SECRET` is unset

`cron/leave-accrual:9`, `cron/reports:8`, `cron/reports/run-scheduled:8` and `cron/billing/daily:24` all compare against a `Bearer ${process.env.CRON_SECRET}` template. If the env var is missing in an environment, that renders `"Bearer undefined"` — which anyone can send. `cron/billing/daily` then walks orgs through trial → past_due → **cancelled** and fires deactivation emails.

`ecosystem/consume/route.ts:11` gets this right (`if (!ECOSYSTEM_SECRET || ...)`). Copy that guard into all four cron routes. Use `timingSafeEqual` while you're there.

### M3. The two report crons ignore multi-tenancy

`cron/reports/route.ts:13-33` counts employees and leaves **across every org** and writes one `report_snapshots` row with **no `org_id`**. `cron/reports/run-scheduled` (lines 19-45) is the same. Post-tenant-migration these produce a meaningless global number and leak cross-tenant aggregates into a table other tenants may read.

**Fix:** loop per organisation and stamp `org_id` on each snapshot.

### M4. PostgREST filter injection via search parameters

User input is interpolated straight into PostgREST filter grammar:

- `recruitment/candidates/route.ts:44-47`
- `assets/route.ts:44`
- `admin-users/route.ts:75`

A `search` value containing `,` or `.` injects extra filter terms into the `or(...)` expression. It cannot reach arbitrary SQL, but it can widen the result set past what the caller should see and reliably 500 the endpoint. Strip `,().*:` from the input, or use `.textSearch()` / a chain of `.ilike()` calls instead of a hand-built `or()` string.

### M5. `parseInt` on unvalidated query params

`payroll/route.ts:29` — `parseInt(searchParams.get('limit') ?? '20')` with no `Math.min` cap and no `NaN` guard. `?limit=abc` gives `.limit(NaN)`; `?limit=999999` streams the whole table. `attendance`, `candidates` and `notifications` all cap correctly with `Math.min(..., 500)` — apply the same here and in `leaves/route.ts:30`.

### M6. Reading a single leave request has no self/manager check

`app/api/leaves/[id]/route.ts` GET is org-scoped only. Any employee can read any leave request by id, including the free-text `reason` — frequently medical or personal.

### M7. Notification spoofing

`notifications/route.ts:77` — `requireAuth()` only. Any employee can POST an arbitrary title and body to any colleague. In-app notifications render as system messages, so this is a workable internal phishing vector ("Your payslip needs re-verification, click here"). Gate to HR roles or system callers.

## Low / hygiene

### L1. `supabase-schema.sql` is badly stale — and it poisoned the last audit

The checked-in schema (58KB, last touched 2026-04-01) contains **zero occurrences of `org_id`**, and no `identities`, `memberships`, `organisations`, `org_settings`, `notifications`, `platform_impersonation_log` or `tenant_visible_audit` tables. It is the pre-multi-tenant snapshot, predating the Phase 0-8 migration.

Consequence worth calling out: `AUDIT.md`'s entire "Schema-code drift" dimension — 14 "confirmed" findings including **Critical #6, "Filtering on non-existent 'org_id' column across 79 route files"** — was generated against this file. Those findings are false positives from a stale artifact, and three adversarial verifiers agreed with each other because they were all reading the same wrong schema. Don't spend time on findings 28-36, 53-56, or Critical 6 until the schema file is regenerated.

**Fix:** `pg_dump --schema-only` from the live project, commit that, and note in the file that it is generated.

Separately, re-triaging the rest of `AUDIT.md` against the current code: Critical 1-5 (`ctx.identityId` used as `employees.id`) **were** real and **have been fixed** — `lib/employee-context.ts` now does the resolution and 24 routes call it. Finding 8 (salary structures) is fixed. Findings 37 (payroll GET role gating), 38 (leave state validation) and 39 (self-approval) are still open and appear above as H5 and H4.

### L2. `.env.example` is stale and misleading

It still advertises `NEXTAUTH_SECRET` / `AUTH_SECRET`, which are dead after the Supabase Auth migration, and omits six variables the code actually reads: `CRON_SECRET`, `IMPERSONATION_SECRET`, `ECOSYSTEM_SECRET`, `DATABASE_URL`, `IMPERIAL_ADMIN_BASE_URL`, `SENTRY_DSN`. A deploy from this template silently breaks impersonation (500 at `impersonation-login:39`) and leaves the crons open per M2.

`.env.local` is correctly untracked — `git ls-files` shows only `.env.example`. No secrets in tracked source.

### L3. Dead code

| File | Status |
|---|---|
| `lib/pg.ts` (78 lines) | zero importers. Its `ensureSchema()` also runs **DDL at request time** and creates a `notifications` table with no `org_id` — which would break `notifications/route.ts:26` if it ever ran. Delete the file and drop the `postgres` dependency. |
| `lib/tokens.ts` (106) | zero importers |
| `lib/validate.ts` (41) | zero importers |
| `lib/auth-utils.ts` (107) | zero importers — NextAuth-era employee lookup, superseded by `lib/employee-context.ts` |

### L4. `requireRole` uses only `ctx.role`, ignoring `isPlatformAdmin`

`lib/session.ts:186-195`. A platform admin with `is_platform_admin: true` but a low membership role is rejected by every `requireRole` gate. Impersonation works around this today, but it is a surprising asymmetry given `AuthContext` carries the flag.

### L5. Fire-and-forget writes without failure surfacing

`lib/audit.ts:56` logs to `console.error` on insert failure and moves on — fine for audit *breadcrumbs*, but §4 of the tenant spec treats `audit_logs` as a compliance record. Same for the leave-balance decrement (`leaves/[id]:196`) and the announcement fan-out insert (`announcements:50`, unchecked). At minimum, route these to Sentry once L6 is resolved.

### L6. Sentry is wired but not installed

`instrumentation.ts` dynamically imports `@sentry/nextjs` only if the package exists and `SENTRY_DSN` is set. Neither is true — the package is not in `package.json` and the DSN is not in `.env.local`. So the shim is a no-op and **the app currently has no error reporting at all** in production. Given C1 and C2 both fail silently, this is what let them survive.

## What's working well

- **Tenant isolation.** 115/116 routes filter on `ctx.orgId` (the exception, `billing/plans`, is a global plan catalogue — correct). Cross-tenant guards on body-supplied ids are present and consistent.
- **Identity/employee resolution.** `lib/employee-context.ts` is a clean fix for what was the last audit's most serious real finding, with a docstring that explains the failure mode.
- **Service-role containment.** `import 'server-only'` in `lib/supabase-admin.ts` makes the key unbundlable, and the split across `supabase.ts` / `supabase-browser.ts` / `supabase-server.ts` / `supabaseTenant.ts` is well documented.
- **Dev tenant switcher.** Genuinely well built — dual-gated (build constant plus `imperial_internal` role RPC), and `team-attendance/route.ts:46-61` **re-verifies the role at consumption time** rather than trusting the cookie. This is the right pattern; it just needs copying to the routes in H5.
- **Money handling.** `lib/money.ts` is decimal.js throughout, and the four remaining `Number()` call sites are on plan seat pricing, not payroll — with explicit comments where CTC was converted.
- **Auth-migration ordering.** The `updateUserById`-before-`verifyOtp` sequencing and its rationale is correctly implemented and documented in three places.
- **`tsc --noEmit` is clean** across ~5,500 lines of lib plus 149 route and page files.
